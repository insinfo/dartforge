# DartForge

[![CI](https://github.com/insinfo/dartforge/actions/workflows/ci.yml/badge.svg)](https://github.com/insinfo/dartforge/actions/workflows/ci.yml)

An experimental **Dart → JavaScript and native (LLVM) compiler**, written in Rust, MIT licensed.
Governing goal: compile any valid Dart 3.6 project with the same semantics as the official Dart
toolchain (VM, `dart2js`, DDC). It is meant to be a shared base for compilation, analysis, an LSP
server, ngdart and web tooling.

What works (verified by execution) and what is missing: **[ESTADO.md](ESTADO.md)**.
Decisions and roadmap: **[PLANO.md](PLANO.md)**. Open items: **[docs/PENDENCIAS.md](docs/PENDENCIAS.md)**.
Most project documentation is written in Portuguese.

## Status at a glance

- **Development JavaScript** (`compile-js`, `dev`, `serve`): ES modules following the DDC
  contract, linked against the official `dart_sdk.js`. The whole differential corpus matches the
  VM byte for byte; `new_sali/frontend` (ngdart) and `limitless_ui/example` run in the browser.
- **Production JavaScript** (`dartforge-jsprod`): one file, pruned runtime, closed world.
- **Native AOT** (`compile-native` / `aot`, feature `nativo`) and an ORCv2 **JIT** (`run` /
  `reload`, feature `jit`) over the same LLVM IR, with a Rust runtime and a tracing GC. The Dart
  SDK is compiled from source. The linker is driven directly (`lld-link`, `ld.lld`, `ld64.lld`):
  a distribution links programs on machines **without MSVC/Windows SDK or Xcode**, and ships
  nothing from those SDKs (import libraries and macOS `.tbd` stubs are generated by DartForge).
- **Build engine** (`dartforge build`): runs `package:build` builders with DartForge's own native
  executor, without the Dart VM. The builders corpus (freezed, drift, json_serializable, mockito,
  built_value, riverpod_generator, sass_builder, …) matches the `build_runner` oracle.
- **LSP** (`crates/lsp` + `editors/vscode`) and the **ngdart generator** (`.template.dart`
  without `build_runner`).

## Benchmark: SIMD that actually beats scalar code

In the official Dart toolchain, rewriting a hot loop with `Int32x4`/`Float32x4` often makes it
**slower** than the scalar version (see [dart-lang/sdk#62618](https://github.com/dart-lang/sdk/issues/62618)
and [#61087](https://github.com/dart-lang/sdk/issues/61087)). DartForge keeps SIMD values in
vector registers end to end (no boxing, no allocation, no runtime calls on the hot path).

### 1. Solid-color blend kernel

[`bench/simd/bin/blend.dart`](bench/simd/bin/blend.dart) is the blend step of a CPU rasterizer,
`(src * a + dst * (255 - a)) >> 8` over 65 536 channels, written three ways with identical output
(checksum `446940672` in every column):

- **scalar**: a plain loop over `Int32List`;
- **SIMD, Dart 3.6 API**: `Int32x4` has no multiply in 3.6, so lanes go through `Float32x4`
  and back, the way real rasterizers are written today;
- **SIMD, Dart 3.14 API**: `Int32x4 * Int32x4` and `>>`, from the 3.14 `dart:typed_data`, provided
  on the 3.6.2 SDK by [`pacotes/dartforge_simd`](pacotes/dartforge_simd) (plain Dart on the VM,
  a `<4 x i32>` instruction in DartForge).

Microseconds per call (lower is better), best of 7 rounds × 400 calls, taking the best of two
separate runs with no other build running:

| Variant | Dart VM (JIT) 3.6.2 | Dart AOT 3.6.2 | **DartForge AOT** |
|---|---:|---:|---:|
| scalar | 104.1 | 69.7 | **71.8** |
| SIMD, 3.6 API | 3 863.9 | 7 428.6 | **95.3** |
| SIMD, 3.14 API | 9 326.6 ¹ | 14 048.6 ¹ | **31.6** |

¹ On the 3.6.2 VM the 3.14 operations are the Dart fallbacks of the extension (lane by lane).

What this shows:

- **The same SIMD source is 78× faster than Dart AOT and 40× faster than the Dart VM** (3.6 API),
  because DartForge does not box the vectors.
- **With the Dart 3.6 API, SIMD still loses to scalar, even in DartForge** (95.3 vs 71.8 µs): the
  API has no integer multiply, so every vector must go to `Float32x4` lane by lane and back.
- **With an integer vector multiply, SIMD wins: 31.6 µs, 2.2× faster than the best scalar code**
  of any of the three compilers (2.3× faster than DartForge's own scalar loop). Beating scalar code needs the right operations in the API (or
  compiler intrinsics); code generation alone cannot remove the lane round trips the 3.6 API forces.
- Scalar code is on par with Dart AOT and 1.45× faster than the Dart VM (JIT).

### What the machine code shows

The production build (`aot --optimize`, `-O2`, baseline x86-64 / SSE2, no `-march`) of the
two loops, from the kept LLVM IR (`DARTFORGE_KEEP_IR=1`) compiled with the same flags:

- `blendSimd314`: the loop arithmetic is vector code: `pmuludq` + `pshufd` (the SSE2 sequence for a
  32-bit lane multiply), `paddd` and `psrad`. The loop still has guard paths with runtime calls
  (an index outside the small-integer range, a receiver of another list class).
- `blendEscalar`: the arithmetic is scalar (`imulq`, `sarq`). LLVM does **not** auto-vectorize
  this loop today, because the loop body still contains guard paths with runtime calls (boxing an
  out-of-range integer, dynamic dispatch for an unexpected receiver). That is why DartForge's scalar
  code only ties with Dart AOT here, and it is an open item: once those guards are hoisted out of
  the loop, LLVM can vectorize the scalar version too.

### 2. Full rasterizer (dgfx)

The `SIMD GAP REPORT` of the dgfx rasterization benchmark (512×512, 14 polygons per iteration),
milliseconds per iteration, min–max of 3 rounds, output images identical across compilers.
Measured on 2026-09-29 while other builds were running on the same machine, so treat the
DartForge column as an upper bound; details in [docs/SIMD-NATIVO.md](docs/SIMD-NATIVO.md) §7.

| Variant (scalar / SIMD) | Dart AOT 3.6.2 | Dart AOT 3.14-dev | **DartForge AOT** |
|---|---:|---:|---:|
| B2D v1 | 6.68–7.09 / 203–268 | 6.67–7.01 / 21.4–21.9 | **5.96–6.06 / 5.68–6.48** |
| B2D v2 Batch | 2.34–5.35 / 21.4–23.8 | 2.02–2.13 / 2.35–2.45 | **1.15–1.22 / 1.38–1.47** |
| B2D v2 Immediate | 2.43–3.99 / 65–86 | 2.08–2.15 / 3.64–3.80 | **1.18–1.32 / 2.59–2.65** |
| SKIA | 2.63–4.08 / 7.9–12.9 | 1.86–1.93 / 1.70–1.74 | **3.41–3.55 / 12.2–12.5** |

- The SIMD rasterizer in DartForge is **about 30–45× faster than on Dart AOT 3.6.2** (B2D v1), and
  in B2D v1 the SIMD path now beats its scalar path, which was 30–40× slower on Dart AOT.
- Where SIMD still loses, the cause is mostly in the benchmark's algorithm: B2D v2 Immediate's
  scalar path only visits the rows marked active while the SIMD path scans the whole tile, and the
  SKIA SIMD path allocates a `List.generate` per row and extracts lanes through a scratch list.

Machine: Intel Core i3-1215U, 7.7 GB RAM, Windows 11; Dart SDK 3.6.2 (stable) and
3.14.0-248.0.dev; LLVM 22.1.8.

### Reproduce

    cd bench/simd && dart pub get
    dart run bin/blend.dart                                   # Dart VM (JIT)
    dart compile exe bin/blend.dart -o blend_dart.exe         # Dart AOT
    dartforge aot bin/blend.dart blend_df.exe --optimize      # DartForge
    # the machine code: set DARTFORGE_KEEP_IR=1, then
    # clang -x ir -O2 -S .df_tmp/blend_df.ll   and look at blendEscalar / blendSimd314

## Build and use

Rust is pinned in `rust-toolchain.toml`. The Dart 3.6.2 SDK is the oracle and provides the SDK
`lib/`; Node 24 runs the JavaScript output.

    pwsh scripts/gerar-dart-sdk.ps1           # dart_sdk.js (once)
    cargo build --release -p dartforge-cli
    cargo run --release -p dartforge-cli -- compile-js examples/hello/main.dart -o dist/hello
    cargo run --release -p dartforge-cli -- dev <entry.dart> -o <out> --packages <cfg>

Native backend (Clang/LLVM 22.1.8; `scripts/env.ps1` sets up the environment):

    cargo run --release -p dartforge-cli --features nativo -- compile-native <entry.dart> -o <out.exe>
    cargo run --release -p dartforge-cli --features jit -- run <entry.dart>

The `jit` feature needs the full LLVM distribution (`LLVM_SYS_221_PREFIX`, in
`.cargo/config.toml`) and `LLVM-C.dll` on `PATH`; see [docs/JIT.md](docs/JIT.md).

## Verify

    cargo test --locked --workspace
    cargo run --release -p dartforge-diferencial               # JS corpus against the VM and dartdevc
    cargo run --release -p dartforge-diferencial -- --producao
    cargo run --release -p dartforge-diferencial -- --nativo --corpus corpus/nativo
    pwsh scripts/ci.ps1 -Frente <name> -Acompanhar            # full CI (ci.yml + pesado.yml)

## Workspace

| Crate | Responsibility |
|---|---|
| frontend | Dart 3.6 lexer, syntax tree and parser (no resolution) |
| elements / types | Element model, SDK from source, types, inference and flow analysis |
| emit_js | JavaScript emission following the DDC contract |
| mundo / emit_js_producao | Closed world and the production profile (one file) |
| gerador_ng | Generator of ngdart `.template.dart` files |
| emit_native / runtime / jit | Own HIR → LLVM IR → objects; Rust runtime; ORCv2 JIT |
| build | Build engine (`package:build` builders, native executor) |
| sass | Sass compiler (dart-sass compatible) |
| abi | Scalar ABI profiles (`abi-info`) |
| dev | Resident compiler (`dev`, `serve`) |
| lsp | LSP server |
| diferencial | Differential harness against the VM, `dartdevc` and our own AOT |
| intern / diagnostics / instrument | Symbols, diagnostics and measurement |
| cli | The `dartforge` executable |

The early exploration (the old `lexer`/`parser`/`semantic`/`hir`/`codegen`/`llvm` track,
`compiler`, `cranelift-jit` and related crates) was removed and is preserved on the
`exploracao-inicial` branch; its documents are in [docs/historico](docs/historico/README.md).

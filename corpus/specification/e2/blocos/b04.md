#### E.2.3 `ensure*`, tokens sintéticos e `TokenStreamRewriter`

**O reescritor** (`fe:parser/token_stream_rewriter.dart`). Todo token sintético nasce com o offset
do token que vinha **depois** do ponto de inserção e comprimento 0; `Token.setNext`
(`fe:scanner/token.dart:676`) grava em `beforeSynthetic` o token anterior no momento da ligação — é
por essa cadeia que `findPreviousNonZeroLengthToken` anda para trás.

| operação | linha | efeito |
|---|---|---|
| `insertToken(token, novo)` | :60 | liga `novo` entre `token` e `token.next` |
| `insertSyntheticToken(token, tipo)` | :211 | `SyntheticToken(tipo, token.next.charOffset)` depois de `token` |
| `insertSyntheticIdentifier(token, [valor = ''])` | :198 | `SyntheticStringToken(IDENTIFIER, valor, token.next.charOffset, 0)` |
| `insertSyntheticKeyword(token, kw)` | :206 | `SyntheticKeywordToken` (usado para `Function`, `with`, `on`, `in`, `while`, `operator`) |
| `insertParens(token, includeIdentifier)` | :29 | `(` `[id]` `)` sintéticos no offset de `token.next`, com `endGroup` ligado |
| `moveSynthetic(token, endGroup)` | :80 | tira o fecho sintético (e o `UnmatchedToken` logo depois dele, se houver) de onde o scanner o pôs, religa-o depois de `token` e **muda o offset dele para `token.next.offset`** (:104) |
| `replaceTokenFollowing(prev, novo)` | :115 | troca um token por uma cadeia (`new` → identificador; `[]` → `[` `]`), herdando os comentários |
| `replaceNextTokensWithSyntheticToken(prev, n, tipo)` | :175 | troca `n` tokens por um `ReplacementToken` (sintético, `length 0`, `scanner/token.dart:812-829`) — `>>` `>` → `>>>` |
| `dropRange(antes, depois)` | :22 | descarta os tokens entre os dois (padrão em declaração de campo/topo) |

Todas (salvo `replaceTokenFollowing`/`dropRange`) lançam `'Internal Error: Rewriting at eof.'` se
`token` é o EOF de offset ≥ 0.

**`ensureSemicolon(token)`** (`fe:parser/parser_impl.dart:4293`):

```
next = token.next
if next == `;`: return next
EXPECTED_TOKEN ';' (ExpectedAfterButGot) em findPreviousNonZeroLengthToken(token)
return rewriter.insertSyntheticToken(token, SEMICOLON)
```

`findPreviousNonZeroLengthToken(t)` (`fe:parser/util.dart:45`): enquanto `t` é sintético de
comprimento 0, `t = t.beforeSynthetic`. O relato cai, portanto, no **último token real consumido**,
com o offset/length dele — nunca no token corrente. Casos que decorrem disso:
- nome sintético antes: `class A { var }` → o `;` é relatado no `var` (o nome sintético é pulado);
  `typedef = int;` → `;` relatado no `typedef` (nome, `(`, `)` sintéticos pulados);
- token estranho consumido pelo contexto de expressão: `x.=> 1;` → `MISSING_IDENTIFIER` e `;` os
  dois no `=>` (o sintético foi posto depois do `=>`, cujo `beforeSynthetic` é ele);
- dois `ensureSemicolon` seguidos sem token real no meio dão o mesmo relato, que o conjunto de erros
  funde (E.2.0): em `case 1 ?? 2:` o `;` aparece uma vez só, no `2`;
- exceção única: em `parseFields` de topo, se falta o `;` e o primeiro token da declaração é o
  identificador `extension`, sai `EXPERIMENT_NOT_ENABLED` (extension-methods) e o `;` é inserido
  sem relato (`:3747-3756`). Alcançável com `// @dart=2.5`: o marcador ganha
  `illegal_language_version_override`, mas o relato do recurso sai assim mesmo (medido, E.2.4).
São 24 chamadas no arquivo, todas com esse comportamento.

**`ensureCloseParen(token, openParen)`** (`:4234`):

```
next = token.next
if next == `)`: return next
if openParen.endGroup.isSynthetic:                 // o scanner já relatou a falta e pôs o `)` no lugar errado
    return rewriter.moveSynthetic(token, openParen.endGroup)      // sem relato do parser
EXPECTED_TOKEN ')' (ExpectedButGot) em next
return openParen.endGroup                          // pula, sem ler, tudo até o `)` casado
```

Chamadas: tipo record `:1635`/`:1662`; parâmetros `:1793`-`:1828`; parênteses/record literal
`:6800`; condição `:6849`/`:6852`; argumentos `:7822`; `for-in` `:8565`; padrões `:10175`/`:10241`.
Quando o `)` é sintético do scanner, o único relato é o do scanner (`ScannerErrorCode.
EXPECTED_TOKEN`, length 1), emitido no fim do `parseUnit` na posição **nova** do `)`: o offset do
token diante do qual o parser parou. O mesmo vale para `]` (`parseArgumentOrIndexStar` `:6484-6496`,
que **também** relata `ExpectedButGot(']')` antes de mover — daí dois relatos no mesmo lugar, um de
cada código; `parseLiteralListSuffix` `:6961-6964`, que só move), `}` de enum (`:2398-2400`) e o
`)` do `catch` (`:8899`, `:8920`), do `assert` (`:9169`) e do import condicional (`:1090`). Sem
movimento (bloco, corpo de classe), o relato do scanner fica onde o scanner pôs o fecho: o offset do
token que provocou o descarte do grupo, ou o EOF (`fe:scanner/abstract_scanner.dart:697-745`,
`appendToken(SyntheticToken(type, tokenStart))`).

**`ensureBlock(token, missingBlockKind)`** (`:4200`):

```
next = token.next
if next == `{`: return next
kind.template != null → relata template(next) em NEXT
kind.message  != null → relata message em TOKEN (o último consumido)
senão (kind nulo, ou sem modelo) → EXPECTED_TOKEN '{' (ExpectedButGot) em next
return insertBlock(token)        // :4220 — `{` e `}` sintéticos, ambos no offset de next
```

| `BlockKind` (`fe:parser/block_kind.dart`) | chamada | modelo → código do analyzer | onde |
|---|---|---|---|
| `classDeclaration` | `parseClass` :2722 | `ExpectedClassBody` → `EXPECTED_CLASS_BODY` (`expected_body`) | token anterior |
| `mixinDeclaration` | `parseMixin` :2954 | `EXPECTED_MIXIN_BODY` | token anterior |
| `extensionDeclaration` | :3178 | `EXPECTED_EXTENSION_BODY` | token anterior |
| `extensionTypeDeclaration` | :3249 | `EXPECTED_EXTENSION_TYPE_BODY` | token anterior |
| `enumDeclaration` | `parseEnum` :2429 | `ExpectedEnumBody` (modelo) → `MISSING_ENUM_BODY` | token seguinte |
| `functionBody` | `parseFunctionBody` :5477 | `ExpectedFunctionBody` (modelo) → `MISSING_FUNCTION_BODY` | token seguinte |
| `tryStatement`, `catchClause`, `finallyClause` | `parseTryStatement` :8823, :8929, :8939 (via `parseBlock`) | `EXPECTED_TRY_STATEMENT_BODY`, `EXPECTED_CATCH_CLAUSE_BODY`, `EXPECTED_FINALLY_CLAUSE_BODY` | token anterior |
| `switchStatement` | `parseSwitchBlock` :8977 | `EXPECTED_SWITCH_STATEMENT_BODY` | token anterior |
| `switchExpression` | :10362 | `EXPECTED_SWITCH_EXPRESSION_BODY` | token anterior |
| `statement`, `invalid`, `null` | `parseBlock` :5608, :8655; `skipBlock` :2352; :4368 | `EXPECTED_TOKEN '{'` | token seguinte |

Os `EXPECTED_*_BODY` compartilham o nome `expected_body` nos diagnósticos (mensagens distintas).
Em `parseFunctionBody`, antes do `ensureBlock`: `;` sem `allowAbstract` → `ExpectedBody`
(`MISSING_FUNCTION_BODY`) no `;`; `=` → idem e segue como `=>`; `return` → idem; palavra ou
identificador seguido de `=>` ou `{` → `UNEXPECTED_TOKEN` nela e segue (`:5430-5480`).

**`ensureColon(token)`** (`:4257`) e **`ensureFunctionArrow`** (`:4268`): `rewriteAndRecover(token,
ExpectedButGot(':' | '=>'), SyntheticToken(offset de next))`. `rewriteAndRecover(token, msg, novo)`
(`:4310`) = relato em `token.next` + `insertToken(token, novo)`. `ensureColon` é chamado na
condicional (`:5882`), em entrada de mapa (`:7176`) e no `switch` (`:9000` depois de `default`,
`:9029` depois do padrão/guarda do `case`). O `:` do `case` é relatado **no token onde o padrão
parou** e o resto da linha vira comandos do caso (ver `case 1 ?? 2:` nos exemplos).

**`ensureLiteralString(token)`** (`:4279`): se `token.next.kind != STRING_TOKEN`,
`rewriteAndRecover` com `ExpectedString` (`EXPECTED_STRING_LITERAL`) em `next` e um
`SyntheticStringToken(STRING, '""', offset de next, length 0)`; depois `parseLiteralString`. Usado
em `import`/`export`/`part`/`part of`/URI condicional (`:864`-`:1270`). O token que estava no lugar
da string **não** é consumido (em `import foo;` o `foo` sobra e ganha `UNEXPECTED_TOKEN`).

**Outras inserções com relato próprio.**
- `ensureParenthesizedCondition` (`:6729`): sem `(`, `EXPECTED_TOKEN '('` (`ExpectedToken`) no token
  corrente + `insertParens(token, false)` — parênteses **vazios**; a condição vira
  `MISSING_IDENTIFIER` no mesmo token e o que seria a condição é lido como o comando seguinte.
- `ensureArguments` (`:7209`) e `parseConstructorInvocationArguments` (`:7219`): sem `(`,
  `EXPECTED_TOKEN '('` (`ExpectedAfterButGot`) no token **anterior** + `insertParens`.
- `parseFormalParametersRequiredOpt` (`:1755`): sem `(`, `missingParameterMessage(kind)`
  (`MISSING_FUNCTION_PARAMETERS`/`MISSING_METHOD_PARAMETERS`/`MISSING_TYPEDEF_PARAMETERS`) no token
  corrente + `insertParens`.
- Vírgula que falta: parâmetros (`:1819-1826`, só se os dois tokens seguintes são `IDENTIFIER`:
  `EXPECTED_TOKEN ','` no primeiro deles; senão `ensureCloseParen`), argumentos (`:7814-7820`, se `looksLikeExpressionStart`),
  listas/mapas/padrões (`:6979`, `:7085`, `:10025`…), parâmetros de tipo (`parseMissingComma`).
- Parâmetros opcionais/nomeados (`:2229`, `:2280`): depois de um parâmetro sem `,` nem fecho,
  `EXPECTED_TOKEN ']'`/`'}'` no token corrente e salto até o fecho casado.
- `parseFormalParameter` (`:2064`): `this`/`super` sem `.` (e sem `= : , ) ] }` depois) →
  `EXPECTED_TOKEN '.'` + `.` sintético.
